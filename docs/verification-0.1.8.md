# 0.1.8 LaTeX PDF 미리보기 지연 개선

- 일자: 2026-10-08. 구현 `9a20535b155c4b0221ba4ce7dcbb48bbabd6379a`, 태그 `v0.1.8`.
- [릴리스 검사](https://github.com/luftaquila/qollab/actions/runs/37663943903). 검증 기록은 구현 태그 이후 문서 커밋으로 추가한다.
- 준비된 상태의 기본 문서 수정은 실제 서버에서 **0.665–0.690초**에 새 PDF가 표시됐다. 첫 빌드와 빠른 연속 수정은 1초를 넘었으며, 모든 문서·수정에 대한 1초 보장은 아니다.

## 변경

- 빈 일회용 작업에서 기본 XeLaTeX 패키지·폰트를 먼저 초기화하고 본문 파일을 읽기 직전에 기다린다. 문서를 전달한 작업은 한 번만 사용하고 삭제한다. 다른 사용자 문서가 남은 프로세스를 재사용하지 않는다.
- 이미지 생성 시 기록한 Quarto의 Pandoc 인자·필터·템플릿을 사용한다. 새 문서의 preamble이 준비된 값과 같은지 확인하고 본문을 전달한다. 글꼴·여백·조판 엔진은 유지한다.
- 표 너비는 같은 프로젝트·문서 세대의 검증된 숫자 정보만 복원한다. 너비가 달라져 재조판이 필요하거나 준비된 경로의 조건을 만족하지 않으면 전체 Quarto 렌더링을 수행한다.
- 자동 빌드 대기를 750ms에서 25ms로, 준비된 작업이 있을 때 큐 확인 간격을 20ms로 줄였다. PDF 결과 저장 후 이벤트를 바로 전달하고 작업 컨테이너 삭제는 응답 뒤에 마무리한다.
- PDF 패널은 최초 PDF를 열 때 PDF.js worker를 만들고 다음 PDF에도 사용한다. 문서별 페이지·폰트 상태는 교체 시 해제하며 패널을 닫으면 worker도 종료한다.
- 미리보기는 다운로드에 제공하는 **최종 PDF 파일 자체**다. 별도의 HTML 미리보기나 다른 조판 엔진을 사용하지 않는다.

## 자동 검사와 출력 일치

- TypeScript/Vue 검사·빌드, Vitest 37개, Python 7개, Chromium 6개 통과. 브라우저 검사는 연속 PDF 교체 시 worker 1개 유지와 패널 종료 시 worker 해제를 포함한다.
- 네이티브 Docker AMD64·ARM64에서 실제 PDF·네트워크 및 자격증명 격리·timeout·참조 캐시 손상 복구·목차/페이지/문헌 참조 변경·운영 Compose 실행·백업 복원을 검사했다.
- 빠른 경로의 본문·이미지·수식·3페이지 문서·목록/링크를 전체 Quarto 출력과 비교한다. 각 페이지를 120dpi로 렌더링한 **모든 픽셀 해시가 일치**했다. 표 너비 변경은 전체 경로로 전환되는 것을 확인했다. 이 검사는 해당 표본의 출력 일치 증거이며 모든 Quarto 문법의 동등성 증명은 아니다.
- [ARM64 출력 비교](evidence/0.1.8/fidelity-arm64.json), [AMD64 출력 비교](evidence/0.1.8/fidelity-amd64.json), [ARM64 백업 복원](evidence/0.1.8/deployment-arm64.json), [AMD64 백업 복원](evidence/0.1.8/deployment-amd64.json).
- 최초 AMD64 실행은 PDF 검사 전 Ubuntu 패키지 목록 갱신에서 지연되어 취소했다. 소스 변경 없이 실패 작업을 새 runner에서 재실행했다.

## 실제 브라우저 지연

이전 0.1.5와 같은 Linux ARM64 서버, 작업 CPU 1개·메모리 2GiB, 한글·표·수식·PNG가 있는 한 페이지 시험 문서를 사용했다. 각 입력 전에 편집기를 열어 둔 채 **40초 기다린다**. 키 입력부터 새 build ID의 PDF 응답과 새 canvas의 내용 표시까지 측정했다. 자동 빌드 대기는 이번 버전에서 750ms → 25ms로 바뀌었다.

| 입력 → 새 PDF 표시 | 0.1.5 | 0.1.8 |
|---|---:|---:|
| 준비된 수정 1 | 5.879초 | 0.665초 |
| 준비된 수정 2 | 5.963초 | 0.690초 |
| 준비된 수정 3 | 6.447초 | 0.675초 |
| 중앙값 | 5.963초 | **0.675초** |

- 관리자 재시작 후 참조 캐시가 없는 첫 수정은 **7.586초**였다. 이 값은 위의 준비된 수정 세 번에 섞지 않았다.
- 준비된 세 번의 서버 저장 확인은 58–128ms, PDF 응답은 623–641ms였다. 실제 작업은 같은 Pandoc/Quarto 필터와 XeLaTeX 1회를 사용했다. PDF에서 새로 입력한 한글도 추출해 확인했다. 브라우저 오류는 0개였다.
- [변경 전](evidence/0.1.5/latency-after.json), [변경 후](evidence/0.1.8/latency-paused.json), [실제 작업 단계](evidence/0.1.8/worker-live.json). 작업 기록의 `warmMs`는 컨테이너 생성 후 입력까지 지난 시간이며, 입력 후 추가 지연에 더할 값이 아니다.

### 바로 이어서 수정

10초 기다린 첫 수정은 **0.876초**, 새 PDF가 나온 직후 다시 입력한 두 번은 **3.793초, 1.280초**였다. 빈 컨테이너는 최대 하나만 준비하므로 다음 작업의 초기화가 끝나지 않은 상태와 준비 작업의 CPU 사용이 지연을 만든다. [연속 수정 기록](evidence/0.1.8/latency-consecutive.json).

첫 빌드·캐시 만료·작업 교체·빠른 연속 입력·여러 사용자의 작업 대기에는 1초 미만을 보장하지 않는다. YAML 설정·Raw TeX·인용/교차참조·추가 수식 명령·중첩 경로·100KB 초과 본문·표 너비 변경 등은 전체 Quarto 경로를 사용한다. 기존 LaTeX 호환성을 유지하기 위한 범위이며 이런 문서의 지연을 준비된 기본 문서 수치로 설명하지 않는다.

| 동작 | 저장 너비 | PDF 그림 너비 | 편집기 그림 너비 |

- 이미지 조작부터 표시까지 4.623 / 1.019 / 3.957초였다. 이 값은 속성 창 조작·드래그 시간을 포함하며 40초 간격의 키 입력 측정과 별개다.

## 배포·격리·정리

- 배포 전 DB와 파일을 같은 시점으로 백업했다. 배포 후 HTTPS 상태, 앱·렌더러 준비 상태와 선언된 이미지 반영을 확인했다.
- 실제 준비된 빈 작업에서 문서 0개, UID 10001, 인증정보와 서비스 계정 토큰 없음, 읽기 전용 루트, capability 제거, CPU 1개·메모리 2GiB를 확인했다. [격리 기록](evidence/0.1.8/isolation-live.json).
- 실서비스 검증은 별도 시험 계정·프로젝트에서 수행했다. 시험 프로젝트·문서 업데이트·문서 세대·사용자·세션과 파일 미러를 제거하고 쓰기 정지가 해제되어 있는 것을 확인했다. 삭제 감사 기록과 배포 전 백업은 보존한다. 실제 사용자 문서는 수정하지 않았다.
- rootless Podman은 이번 릴리스에서 재실행하지 않았다. 실행 설정은 제공하지만 이번 Docker 검증과 구분한다. 실제 Google 계정 로그인도 이번 성능 검증에서 재시험하지 않았다.
- 로컬 상시 앱·DB·Podman 설치를 복원하지 않았다.

## 프런트엔드 측정

Vue·Yjs 단일 런타임과 초기 화면의 편집기/PDF 분리 로딩 검사를 통과했다. CI의 gzip 크기는 앱 셸 **41,071B**, 편집기 **459,127B**, PDF 모듈 **129,349B**, PDF worker **376,488B**다. [번들 기록](evidence/0.1.8/bundle-ci.json).

CI Chromium, loopback, 단일 클라이언트, 19,795B 문서에서 입력→animation frame p95 **16.7ms**, 문서 전환 **108–226ms**, JS heap **9.69 → 11.58MB**였다. 이 프런트엔드 표본은 운영 PDF 생성 지연과 별개다. [측정 조건과 원본](evidence/0.1.8/performance-ci.json).

고정 digest는 [versions.env](versions.env)에 있다. 기존 `.env`의 `APP_IMAGE`, `RENDER_IMAGE`를 해당 값으로 갱신하고 Google 설정·기존 볼륨은 유지한다.

```sh
docker compose pull
docker compose up -d
# Rootless Podman: 엔진 소켓 설정은 operations.md 참고
podman compose -f compose.yaml -f compose.podman.yaml up -d
```

열려 있던 브라우저는 새로고침해서 새 편집기와 PDF 모듈을 불러온다.
